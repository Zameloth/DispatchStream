# Stateful validation for late/duplicate/conflicting/orphan-END

ADR 0003 scoped DISP-1 to stateless checks only and deferred late, duplicate, conflicting, and orphan-END detection to a later pass, to piggyback on state store infrastructure DISP-2/3 already needed. This ADR is that pass. We chose a **second validation stage**, per stream, built on the Kafka Streams Processor API (`KStream.processValues()` with a `FixedKeyProcessorSupplier` and an attached `KeyValueStore`) rather than folding these checks into the existing `ValidationStep<T>` chain: `ValidationStep` is deliberately a pure `T -> Optional<String>` function (ADR 0004), with no access to a store, the record key, or the record timestamp, none of which late/duplicate/conflicting/orphan-END can be decided without. `TopologyProducer.validateAndRouteToDlq` (stateless) now returns `ValidationOutcome.Valid<T>` instead of bare `T`, preserving the original raw message so the new `applyStatefulValidation` stage can still build a byte-for-byte `DlqEnvelope` if it rejects a message the stateless stage already accepted. Both stages share one `routeOutcomesToDlq` helper, so there is a single DLQ-routing code path for both.

The trade-off: this introduces the repo's first Processor API code and first explicit state stores (previously only DSL `Materialized` stores, cf. ADR 0002/0006), a real increase in mechanism for four rules. We accepted it because `ValidationStep` cannot express these rules any other way, and CONTEXT.md requires all four categories.

## Lateness needs no stream-time tracking

CONTEXT.md defines "late" as arriving more than 6 minutes after the event's own timestamp. We compare the Processor API's `Record.timestamp()` (the Kafka record timestamp — arrival time) directly against the parsed business `timestamp` field (`Timestamps.isLate`), both stateless and independent of Kafka Streams' internal stream-time tracking. We rejected using `context.currentStreamTimeMs()` (an earlier design note in this project's scratch notes suggested it): stream-time is a task-wide, monotonically-advancing watermark, not "when did this specific record arrive," and every existing test in this repo (e.g. `DemandByZoneTopologyTest`) already establishes record timestamp as the arrival-time proxy via `pipeInput(..., Instant)` — the business timestamp was simply unused for anything until now.

## Dedup/conflict store: lazy expiry, no punctuator

Duplicate/conflicting detection needs "was this identity seen recently, with what content." Each stream gets one persistent `KeyValueStore<String, ⟨Stream⟩Occurrence>` (`RideRequestOccurrence`/`DriverLocationOccurrence`/`TripEventOccurrence`, each pairing the last-seen value with its arrival epoch-millis), keyed by that stream's identity from CONTEXT.md (`request_id`; `driver_id|timestamp`; `trip_id|event`). Expiry is checked lazily on lookup (`arrival - storedSeenAt > 6min` ⇒ treat as unseen) rather than swept proactively by a scheduled `Punctuator`. We accepted the resulting unbounded store growth under sustained load as a known limitation rather than engineering active cleanup now: the vendored dataset (~192k messages) and this project's scope don't call for it, and a punctuator can be added later without changing the public store shape if it ever does.

## Orphan-END reuses the trip-event dedup store

Trip-event identity is `(trip_id, event)`, and a trip has at most one `START` and one `END` (CONTEXT.md). Looking up key `trip_id|START` when processing an `END` answers "was a START seen, and when" using the *same* store already built for dedup — no second store. An `END` is orphaned if that lookup is absent or expired (>6 min old), independently of whether the `END` itself is a duplicate (duplicate is checked first; an already-duplicate `END` never reaches the orphan check).

## No "conflicting" category for ride requests or trip events

CONTEXT.md defines "conflicting" only for driver locations (same `(driver_id, timestamp)`, different `lat`/`lon`) and defines "duplicate" everywhere as matching identity **and** matching content. For ride requests and trip events, an identity match with differing content is therefore neither a defined duplicate nor a defined conflict — we let it through as valid rather than inventing a conflict category CONTEXT.md doesn't specify. Driver-location conflict comparison is on `lat`/`lon` only (not the full record), since that's the field CONTEXT.md calls out as the contradiction.
